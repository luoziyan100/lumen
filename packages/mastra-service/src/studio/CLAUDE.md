# studio/
> L2 | 父级: ../CLAUDE.md

新形态的产品领域：主题是基本单元，材料在全局资料库、主题只引用，产出写在主题的白板上而不是对话里。白板自 2026-11-19 是人与 AI 共画的 Excalidraw 画布；旧区块表保留只读，不再写入。产品合同在主检出的 `doc/studio/model.md`（规则 R1–R17），本模块只落存储与 HTTP；消息、运行、挂起仍归 Mastra。

- `types.ts`：主题、资料、主题材料、白板、区块、出处、版本、写入来路与沉淀（条目/片段/链接/报价单/邀请/说话习惯）的纯类型，服务与桌面共用。Readings too: `Reading` (sections in order, each item in `paragraphs` is a `ReadingParagraph` union: prose text `{id, kind?:'text', text, source}`, `table`, `diagram` (Mermaid), or `widget` (HTML), each with `source` either `{kind:'paper', page?, quote}` or `{kind:'inference'}`) and `ReadingSummary` for the list.
- `errors.ts`：`StudioError`，带 HTTP 状态的中文错误；同一句话既给人看，也作为白板工具的拒绝文本给模型看，所以要写清下一步。Optional `detail` fields go into the HTTP body next to `error` (R17: `reason`, `blocks`). Every StudioError also has a `code` from `http/error-codes.ts` and optional `params`; the UI shows text by code, models still read `error`. `notReferenced(itemId)` is the one R15 refusal: read_material, reading_view and reading_write give the same sentence.
- `content.ts`：白板内容合同唯一真源。画布合同：`CANVAS_LIMITS`、元素 id、AI 画的 ElementSkeleton 片段（`skeletonSchema`）、AI 改自己元素的补丁（`patchSchema`）、擦除理由；只验形状，转换成元素由桌面用真实字体完成。旧区块合同（text/ladder/table/widget、出处、摘要）只剩旧数据在用。
- `db.ts`：在 `catalog.sqlite` 建 studio 表（与阅读游标同文件，不碰 `mastra.sqlite`），外键开启；`transaction` 是同步立即事务；`sheet_selection` (the user's selected sheet per topic) and `run_targets` (each run's fixed write target, keyed by thread) are additive tables created the same way; P1 沉淀五张表（条目/修订/链接/报价单/邀请）与全局 `speech_habits` 同为新增表；`sediment_links` 故意不带块外键`pending_deletions` 是删除记账表；2026-11-19 共画画布只新增表：`canvas_elements`（每个 Excalidraw 元素一行，按 id 合并、高版本胜，作者由服务端记）、`canvas_files`（图片字节）、`canvas_ops`（等桌面排版的 AI 写入）、`canvas_erasures`（R5 回收记录）、`canvas_snapshots`（R7 每次运行一份）、`canvas_viewports` 与 `canvas_glances`（每张白板一行，覆盖写、不留版本）；`blocks`/`sheet_versions` 原样保留、不再写入；`sediment_links` 故意不带块外键：删白板后链接留 titled 供展示（S3）；`readings` (one per topic × library item, cascading from both) and `reading_sections` (ord unique per reading, paragraphs as JSON, stamped with the writing thread and run) are additive too； 旧库缺的列（资料的作者/年份/arXiv 编号/标题来源）只在服务启动时按 `PRAGMA table_info` 补加（幂等，只加列不改数据）；`schema=false` 只打开不改结构、缺列就拒绝。
- `board.ts`：白板与写入目标的唯一存储。R16: `select`/`selection`/`selectedSheet` (selection, else newest live sheet), `runTarget(threadId)` captures the selection once per run and keeps it through waits, suspension and restart, `endRun` releases it; `peekTarget` serves reads that may run outside the run (experts' board_view): stored target, else today's selection, never captured; `writeTarget` refuses a folded or gone target. `pendingSheets(threadId)`（自该对话上个快照以来改过的白板，挂起续跑换 runId 也不丢）+ `writeVersion` 给「每次运行一个快照」（R7），快照由画布写。R17: `deleteSheet(topicId, sheetId, { confirmed, busy, since })` deletes in one transaction — refuses the target of a running/waiting run (or a target captured after the activity read began), asks for confirmation when the sheet has content (live canvas elements plus old blocks; the 409 body also carries `settled`: how many takeaways lean on its old blocks), moves the selection to the next sheet by ord (else the previous, else none) when the deleted sheet was the selected one, then deletes the canvas rows (cascade), old blocks, versions, target, selection and invite rows and the sheet — sediment links and entries survive by design. `canvas` is the sheet's CanvasStore. Default titles of new sheets skip numbers already in use (deletes can lower the count).
- `canvas.ts`：画布的唯一写入路径（R4）。`save` 是用户的保存：按 id 合并、高版本胜，同版本以服务端为准并在 `kept` 里退回；作者由服务端记，删除（墓碑）也是保存。AI 的画与改只排队成 op（服务端不量字），桌面用真实字体排好后 `commit`：元素记为 AI 的，用户的元素只能多出绑定，墓碑不复活。`erase`（R5）：AI 自己的直接删；用户的线条与形状软删进回收记录，可 `restore`/`dismiss`；用户的字一律拒绝。另有视口、图片文件、glance（桌面最新的 PNG 与它对应的场景版本）、每次运行一个快照（R7）、`changedBy`、`liveElements` 与 `locate(topicId, id)`（元素在本主题哪张白板上；别的主题一律找不到）。
- `glance.ts`：模型看白板的唯一途径（Q6），只在模型能看图时注册。请求处理器把本轮目标白板最新的 glance 作为一条用户图片放进当前请求，一次请求至多一张；PNG 不进持久消息、资料库与记录。`board_look` 最多等约 5 秒，等一张跟上 AI 最新写入的画面。
- `deletions.ts`：R20 删除记账 `pending_deletions`（主题或对话一行）。记账后对象即隐藏并拒绝运行；删除最后一步与 catalog 行同一事务删掉记账。它是日志，不是软删除标记。
- `topics.ts`：主题增改（新主题同事务建第一张进行中白板，没有种子内容；正在删除的主题不入列表、按 404；改名去空白，空标题 400 `topic.title_empty`）与主题引用：引用/取消引用/阅读进度/被当前区块引用数。取消引用不动区块（R10）。
- `library.ts`：全局资料库。按 sha256 去重（并发同内容由唯一约束裁决），原件落 `library/<id>/` 后 chmod 0400；链接收入时 PDF 存原件，网页存抽出的正文与来源 URL；arXiv 任何写法都取 `arxiv.org/pdf/<id>` 存 PDF、出处记摘要页，标题按 `resolveTitle`（给定 → API → PDF 信息 → 首页大字 → 文件名）；`location` 给原生「系统打开」核对后的真实路径（只认 `library/<id>/` 下的普通文件）；`refresh`/`replaceOriginal` 只给补取用；INSERT 一律写明列名（旧服务按位置插入在补列后失败的教训）。
- `titles.ts`：标题回退链里与 PDF 有关的纯规则：清洗（空白/`[编号] `前缀/≤200 字）、Info Title 排除（空、乱码、文件名、软件名）、首页最大字号所在的横排行；小型大写标题的词身是同一基线上 ≥0.6 倍字号的大写块，收回并还原小写，只有字号不同又贴着的块才连成一个词（同字号照旧补空格，空格常是被滤掉的独立空白块）；`TITLE_RANK` 让补取只升不降。
- `backfill.ts`：显式补取命令（不在启动时跑）：先出计划，再 VACUUM INTO 备份 catalog 与受影响的 `library/<id>/` 并写 SHA256 清单，最后按同一条目换原件/重算标题；arXiv API 请求间隔 3 秒；只填数据不改表结构（以 schema=false 打开，库未被新服务启动过就拒绝）；对正式数据须先经负责人确认，且在正式服务换成含本迁移的代码并重启之后。
- `reading.ts`: the only writer of readings (living reading). `write` appends a section or replaces one whole by id in one transaction, mixing prose/table/diagram/widget blocks; `insert` adds one block into an existing section right after `afterId` (or at the end) up to `sectionMax` (12), checking the reference (R15) and the caps (`READING_LIMITS`: 12 sections, 8 blocks per write, 12 max per section, 600 characters per prose paragraph, 8KB Mermaid, 64KB widget HTML; quotes 8–400 characters after normalisation); `patch` (2026-11-21) edits one block in place: 1–20 `{old,new}` edits applied in order to its text/mermaid/html, each `old` found exactly once (else refused naming the edit and the next step), table edits refused, `title`/`caption` replaced (`''` deletes), widget `params` replaced (`[]` deletes), source never changed; the result is rebuilt as a write input and passes the same `normalizeBlock` rules under the old id, section and position, so title-keyed widget values survive; an empty patch is refused; refusals reuse `reading.block_invalid` (no new error code); no versions. `readingBlockInput` / `readingInput` / `readingInsertInput` / `readingPatchInput` are the zod shapes the tools share; `normalizeQuote` (NFKC, whitespace collapsed) and `quoteFound` (compares with whitespace removed, since PDF text breaks lines anywhere) are the one quote rule. Section ids are `s` + 10 hex and block ids `p` + 10 hex, short so the model can copy them back. A widget block may declare `params` (P1, 2026-11-20); every widget block passes `widget-check.ts` before anything is stored.
- `reading-tools.ts`: the AI's only way to write a reading (main agent only): `reading_view({itemId, blockId?})` (returns block ids and compact summaries, omitting raw widget HTML but showing a widget's declared `params`, so a rewrite keeps their names; with `blockId`, that one block whole with its section id and title, widget html included; an unknown id points back at the plain view; both the description and the plain result say the source lives in the reading store, not the workspace, so the model never hunts with list_files/read_file/run_code), `reading_widget_guide()` (read-only, returns `WIDGET_GUIDE`; fetched before writing a widget), `reading_write({itemId, sectionId?, title, paragraphs})`, `reading_insert({itemId, sectionId, afterId?, block})` and `reading_patch({itemId, blockId, edits?, title?, caption?, params?})` (read the block first; no quote is rechecked because the source cannot change; the description warns that a widget's title keys the person's values); the description says the quote is shown under its block (point at it, do not copy it), titles carry no ordinal (the view numbers sections; code never strips one), and the `widget` hint is its shape plus 「写之前先调 reading_widget_guide」 (P5, 2026-11-20: how to write a widget is fetched on demand, not carried by every request). The program checks only what would break a promise: the material is this topic's (R15), each paper quote occurs on the cited page of the same PDF page cache read_material uses (materials without pages take no page and the quote must occur in the text), and the caps. What medium (prose vs table/diagram/widget) and how deep is the model's call. Refusals name the item and the next step (read the page with read_material, or call reading_view for section/block ids). Topic, thread and run come from the board's trusted writer.
- `widget-check.ts`: the widget half of `normalizeBlock`. `widgetParamInput` is the zod shape of one declared parameter (`range` min/max/step/default/unit?, `toggle` default, `choice` 2–6 `{value,label}` and a default among them); `normalizeParams` checks by hand what zod does not name (≤6 params, `^[a-z][a-zA-Z0-9]{0,31}$` names unique in the block, labels ≤40, min<max, step>0, default in range, unit ≤12), so a refusal names the block and the parameter. `checkWidgetHtml` is the static self-check (P4): classic inline scripts compile under `node:vm` `Script` and never run (data scripts such as `application/json` are skipped), `type="module"` is refused, `src`, `<link href>` and CSS `url()` with `http:`/`https:`/`//` are refused anywhere in the html while an `<a href>` passes (the receiver posts its click to the host, which opens it outside), `fetch(`/`XMLHttpRequest`/`WebSocket`/`EventSource`/`import(` are refused in script bodies and `on*` handlers only (prose that mentions them passes), and declared params must be read (`lumenParams` or `lumen:params`) while undeclared ones must not be. The receiver's CSP (`connect-src 'none'`) would block the same things at runtime; the check turns a blank widget into a refusal the model can act on. All refusals use the existing `reading.block_invalid` code.
- `widget-guide.ts`: `WIDGET_GUIDE`, the Chinese widget handbook (≤4KB: visual grammar, declaring and reading params, changing a widget by reading_view(blockId) then reading_patch with the old names and title, do not redraw declared controls, `__widgetSendMessage` only after a click, hard limits, one complete example) and `WIDGET_EXAMPLE`, the example itself; tests run the example through `widget-check` so the handbook never teaches a refused page. It ships with the code, not as a user skill: handbook, receiver and check are one contract.
- `reading-question.ts`: the service's reader of what the desktop writes in the person's name. A reading question (`MODEL_TEXT.askReading`: `> quote` lines, `— 解读《item》· section（段 blockId）` (the block id since 2026-11-21; older questions have none), a blank line, the words) gives only its words; a question asked from a widget is the same format with two program lines as its quote (`小实验「title」`, `当前参数：…`); the write request, a widget's message (`— 小实验`, sent only right after the person touched the widget), the diagram fix request and the widget fix request (`解读里的小实验运行出错：`) give nothing; a typed message loses the upload list appended to it. So sediment (R13) never takes program or AI text for the user's. The UI keeps its own parser; `ui-client/tests/reading.test.ts` feeds the real MODEL_TEXT output to both and requires the same result.
- `studio.ts`：一条 catalog 连接上组合主题/白板/沉淀/资料库/解读五个存储（也暴露连接给补取备份与工具的块归属查询）；server 与之后的白板工具共用同一实例。另挂删除记账 `deletions`。
- `sediment.ts`：沉淀唯一存储（R13）。条目只经用户 HTTP 建/改（改留修订行）/删（删释块回 current，与链接同事务）；`quotePlan` 是「只删不改」的子序列规划器（纯函数，无口癖表：空白串可折成一个空格，返回被删片段供删除线与习惯表）；报价单（AI 递回的原话 + 片段）确认时对用户划完的最终文本再验一遍，并按「留下=kept、放回=restored」累计进全局 `speech_habits`（丢弃不计，AI 无写工具）；每张白板的邀请最新覆盖。
- `sediment-tools.ts`: the AI's only contact with sediment (S4, main agent only). `sediment_invite({question, elementIds?})` may point at live elements of the run's target sheet, or at none, and stores the invitation. `sediment_quote({text, elementIds?})` has the service search this thread's user messages, newest first, for the first one the text passes delete-only against (the model never sees message ids; it flushes the run's messages first, because since Mastra 1.84 an auto-approved tool runs before its step is saved); a reading question counts by its words only (`userWords`, G1). It stores an offer and creates no entry.
- `tools.ts`：资料库访问边界（R15）：`createMaterialAccess`（研究网络必传，arXiv 收入用） 只放行受信会话所在主题引用的条目（未引用/不存在/越界同一句 404），PDF 分页缓存按 sha256；`text(item, bytes)` gives the plain text read_material shows, shared with the reading quote check；list_materials/read_material（按页或偏移读，推进阅读进度）；`intake` 供研究工具 to_library 收入并引用，arXiv 链接一律收 PDF（已取到的字节直接复用）。
- `board-tools.ts`：AI 上白板的唯一通道：board_view（专家也有；只给结构：元素 id、类型、作者、位置大小、文字或标签、箭头两端，以及用户看的视口，不给图）/board_draw（ElementSkeleton 片段，排队等桌面排版）/board_update（只改 AI 自己的元素）/board_erase（R5）。主题、运行与本轮写入目标（R16）从受信主会话推出（专家的 board_view 读父会话的目标）；`topicState` 每次请求注入主题现状（用户的沉淀新在前、已有解读清单（标题行指路：reading_view 带 blockId 看块原文、reading_patch 局部改、reading_insert 原地补块）、本轮目标画布：计数、视口、有字的元素每个一行 + 引用材料 + 说话习惯一小段〔S14，约 120 token 折进同一上限〕；目标已收起时如实说只读），按估算 token 硬上限 1500、新的优先，超出提示用 board_view 看全。画布没有容量上限，旧的 supersede 与写满拒绝随区块退役。
- `routes.ts`：认证后的 HTTP。主题（状态灯由 `topicId:` 前缀汇总原生运行/等待）、白板（列表的 writable 在没有进行中的那张时为 null，不报错；`selected` is where the next message writes, `target` the sheet of the run in progress (only while it runs or waits); `PUT /topics/:id/selection` records the user's tab; ＋ 新开一张并选中）、资料库（multipart 上传或 JSON 链接，可顺手引用到主题）、原件（ETag=sha256）、原件本机位置（只按条目 id，供原生系统打开）、主题引用增删。画布（2026-11-19）：`GET /sheets/:id/canvas`（场景：元素含墓碑、待排版的 op、未处理的回收记录、视口；ETag/304）、`PUT /sheets/:id/canvas`（用户保存，回 `kept`）、`POST /sheets/:id/ops/:opId`（桌面提交排好的 AI 元素；已提交过答 409 `board.op_done`）、`POST /sheets/:id/erasures/restore|dismiss`、`PUT /sheets/:id/viewport`、`PUT /sheets/:id/glance`、`GET /sheets/:id/files/:fileId`、`GET /topics/:id/elements/:elementId`（`{sheetId}`；元素 id 是画布内的随机 id，不做全局键，别的主题、已删或不存在一律 404 `board.element_missing`）。收起的白板拒绝用户保存（409 `board.sheet_closed`）。R17: `DELETE /topics/:id/sheets/:sheetId` (only the user; `?confirm=true` for a sheet with content, otherwise 409 with `reason: 'confirm'`, `blocks` (the content count) and, when takeaways lean on its old blocks, `settled`; 409 `reason: 'target'` for the run's target). The old block reads (`GET /sheets/:id`, `GET /blocks/:blockId`) retired with the blocks. Topic archive goes through the server's idle guard: 409 `topic.running` while it runs or waits.
  Readings (P1-2): `GET /topics/:id/readings` (`{items}`, newest first) and `GET /topics/:id/readings/:itemId` (ETag/304; 404 `reading.not_found`). Read-only: readings are written only through reading_write.
  沉淀（R13，S2/S14）：`GET/POST /topics/:id/sediment`（条目新在前 + 待确认报价单；建条目只走这里——offerId+text 是确认报价单，text 为用户划完的最终文本）、`PATCH/DELETE /topics/:id/sediment/:entryId`、`DELETE /topics/:id/sediment/offers/:offerId`（丢弃）、`GET /sheets/:id/invite`、`GET/DELETE /lumen/speech-habits(/:fragment)`（只读与逐条删）。

决策：
- 白板存数据库不存文件：通用文件工具碰不到（R4），合并、作者与快照才能在一个事务里成立。
- 共画画布（2026-11-19）：服务端不量字，所以 AI 的写入先排队，由桌面用真实字体排版后提交；提交前不进场景，用户的下一次保存就不会认领 AI 的笔画。旧区块表不删，旧沉淀链接只显示标题。
- R16 (2026-11-13): the AI writes on the sheet the user selected when the run started, fixed for the whole run; switching tabs mid-run does not move it. Clients that never select get the newest live sheet. The AI never opens or switches sheets; ＋ is the user's.
- arXiv 补取在同一条目上换原件：id、主题引用、阅读进度与白板出处都不动；换成的 PDF 若已是另一条目则跳过不合并。
- R17 (2026-11-14): only the user deletes a sheet; nothing is soft-deleted and its versions go with it. Confirmation is a query flag the client sends after the service answered 409 with the content count, so the count shown is the service's. The running/waiting test is the sheet list's; a target row newer than the activity read also blocks, which closes the gap between the async read and the synchronous transaction.
- P1-2 (2026-11-17): a reading is the AI's structured account of one material, kept next to the board in catalog.sqlite rather than as a file, so the quote check and caps hold in one transaction and the Reading view refreshes by ETag like the board. Paper quotes keep the original's language; the check is against the original text, so a translated quote never matches.
- 区块 ID 短（`b` + 10 位 hex）便于模型回填；主题/白板/资料 ID 用 UUID，主题 ID 满足会话身份 `topicId:taskId` 的 safeId 规则。
