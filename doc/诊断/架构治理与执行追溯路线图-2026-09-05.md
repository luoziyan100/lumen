## 架构落点

```text
protocol/                 解码命令与 requestId；固定目标任务，返回对应响应
runtime/ + subagent/      拥有执行生命周期、父子关系、上下文来源和取消请求
core/                     通过窄类型与采集端口报告执行事实，不依赖数据库或 UI
adapters/ + transport     保存最终提供商请求、逐次尝试、原始响应及解析结果
tools/ + workspace/       保存工具结果、实际退出信息及受控文件变更收据
storage/                  原子保存任务事实、证据元数据与内容引用
ui-client/                投影任务状态，标记问题，按需查询证据
```

沿现有端口扩展，维持 Tauri 薄客户端、独立 Node 服务和 SQLite 存储。新增的窄类型或存储模块必须各有实际消费者，不向 `ToolContext` 填入数据库、UI 和供应商对象。

`tasks/task_events` 继续管理任务状态与恢复。详细证据可以使用关联表和内容文件，但不能另立一个裁决任务状态的 trace 状态机。JSONL 是可重建的阅读/导出投影，导出失败不能伪装成数据库提交失败。

数据库提交成功后发布事件；发布缺口通过已提交序号补齐。无需声称数据库、文件系统与 WebSocket 可以原子提交。

## 最小证据契约

| 标识 | 职责 |
|---|---|
| requestId | 关联一次客户端命令及其成功、错误、超时或断线结算 |
| taskId / turnId | 标识会话及其中一次执行；使用现有概念，不重复创造同义实体 |
| agentId | 标识主代理或具体子代理实例，角色名不能代替实例身份 |
| operationId / parentOperationId | 宿主分配的模型或工具操作身份及嵌套关系 |
| causeEventId | 需要时指向触发该操作的消息或事件，不能用时间顺序代替因果 |
| attempt | 区分同一逻辑请求的重试；供应商 toolCallId 作为关联字段保留 |

记录同时携带 schemaVersion、时间、类型和内容引用。显式区分系统观测、模型自述、恢复时合成的信息和外部验证结果。

requestId 不自动提供幂等性。恢复若开启新 turn，应关联此前执行，不改写其历史身份；后台辅助模型调用关联原触发对象，不读取可能已经切换的当前 turn。

已有 `tool_call` 可承载写前意图，无需再复制一份等价开始日志。关键意图持久化失败时，不启动有副作用的工具。完成后记录关联结果；缺少结束记录的调用由取得独占权的恢复流程标为结果未知。

取消请求、工具响应取消、进程实际退出是不同事实。等待超时不证明动作停止；实际副作用未知时不能自动重新执行写入或外部操作。现场内容符合预期也只能证明当前状态，不能单独证明是哪次调用造成。

## 内容采集范围

### 模型

- 保存实际使用的模型配置、system prompt、工具定义和最终发送的请求；采集点必须在上下文折叠、视觉转换和提供商格式转换之后。
- 保存上下文来源及变换记录，使调查者能区分原输入、给模型的表示、截断与压缩；只保存最终请求不能解释内容为何被移除。
- 原始响应与解析后结果关联，重试、流式中断和解析失败有独立记录。流式正文使用有界写入方式，不把每个 token 都变成一条任务事件。
- 主代理、子代理、识图等模型调用使用共同采集边界；标题与图表修复也须标明调用用途，并关联其原始触发事件。

### 工具与产物

- 统一保存参数、执行结果、错误类别、耗时和可获得的退出信息；保留给模型的摘要与调查用的结构化结果。
- `write_file/edit_file` 从实际触及的文件开始，保存写前/写后内容版本及关联操作；按需保留被覆盖内容，不要求整个工作区每次全量快照。
- `run_code` 首先保存不可变脚本、已采集输出、截断标记和实际进程退出信息。任意代码的全部文件及网络副作用仍有覆盖边界，不能把目录对拍宣称为完整审计。
- 大内容使用按内容标识的持久引用；只保存 hash 或可变路径不能还原原文。证据存储位于 Agent 可写工作区之外，并纳入执行器资源边界。

### 存储与性能

- 内容文件先完成写入，再提交引用它的数据库记录；数据库失败留下的孤立内容可以清理。缺失文件须能检测，不构造虚假的跨资源原子性。
- 身份凭证不进入记录；业务内容按本地访问和保留策略管理，导出时脱敏并标记删减。过期、丢失和截断必须可见。
- 证据正文不进入聊天 reducer，不随流式增量反复传给 UI；查询按操作与内容引用加载。
- 关键开始/结束事实与可选调试正文明确区分；正文存储故障应留下缺失标记，存储策略与性能预算在上线前验证。

## 每批验收

| 批次 | 必须证明的行为 |
|---|---|
| 1 | 默认启动拒绝无凭证请求；假密钥文件在真实执行沙箱内不可读；非法消息及 handler 异常不会终止服务；统一验证入口执行两包必需检查 |
| 2 | 第二实例在迁移/恢复/写入之前被拒绝；故障注入后主表与事件一起回滚；迁移可重启；准备失败释放执行登记；开始/结束或未知结果可按操作定位；在线与回放消费相同 durable 事实 |
| 3 | 并发乱序响应各归其请求；上传中切会话不改变命令目标；公开子代理都经过同一治理路径；重连与历史回放不覆盖当前执行状态 |
| 4 | 修改 settings、memory、skill 和源文件后仍可还原历史实际请求；解析失败、重试及取消可定位；文件证据不被后续执行覆盖；存储失败与内容缺失不伪装成完整记录 |
| 5 | 标记回答可定位具体 turn/模型/工具及预期结果；脱敏诊断包可独立检查；替换真实模型响应和工具执行的受控回放不产生真实副作用；已知坏例进入相应回归或质量评估 |

每批先补本批失效模式的行为测试再改代码，完成后交 Grok 做内部独立验收；失败由 Grok 直接反馈子 Agent 修复，通过后自行推进下一内部批次并检查保持性。这里的“每批交付”是主模型内部交付，不是每批交原审查者终审。

终审节点统一遵循总执行 Spec v2.0 第 6-8 节：Grok 内部完成批次 1-5、F01-F24 和保持性，在同一整体候选上完成合同核对、整体回归与安装验证，登记 `MAIN_PASS` 后统一交终审；终审失败回到内部修复循环。批次 4-5 已纳入当前授权，不再等待批次 1-3 单独终审或另开 Spec。内部批次通过不触发用户转发或原审查者终审。

服务逻辑修改按项目要求重装 launchd；UI 或用户可见界面修改完成后构建、重装并打开桌面 App。

历史查看、恢复续跑、录制结果回放、重新调用模型是四种能力。重新调用模型用于评估变更效果，不承诺重现相同答案；回放工具结果不能证明外部世界当时的全部状态。
