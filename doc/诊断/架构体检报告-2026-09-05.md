### A01: 默认启动关闭鉴权

证据: [service.ts:182](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/service.ts:182)、[server.ts:49](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/server.ts:49)、[server.ts:77](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/server.ts:77)。

实际 token 为 `config.token ?? process.env.LUMEN_TOKEN ?? ''`；HTTP 和 WS 都只在 token 非空时校验。HTTP 同时允许任意 Origin，WS 没有来源校验。可访问本机端口的无凭证客户端可以提交任务、读取工作区资产或修改模型配置；具备本地网络访问能力的网页也在此范围内。

问题是信任边界依赖配置是否碰巧存在。根 CLAUDE.md 的“所有 WS 必带 token”和 service 的随机 token 注释已经失真。

建议: 默认生成凭证，HTTP/WS 通过同一认证入口，校验允许的浏览器来源；禁止以空配置隐式关闭保护。验收需覆盖默认启动、缺凭证、错误凭证、正确凭证和来源限制。

### A02: 沙箱读取策略遗漏正式支持的密钥路径

证据: [service.ts:223](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/service.ts:223)、[sandbox.ts:50](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/tools/env/run-code/sandbox.ts:50)、[sandbox.ts:67](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/tools/env/run-code/sandbox.ts:67)。

服务从包目录 `.env` 和 `~/.lumen/.env` 读取配置，但 Seatbelt 的有限禁读列表只覆盖 `settings.json`、`agent-service.json` 等路径。`allow default` 允许读取遗漏的 `.env`。即使工具子进程禁网，读到的内容仍能随工具结果发送给外部模型。

隔离复现: 临时 fake HOME 中写入仅含 `AUDIT_SENTINEL_ONLY` 的 `.lumen/.env`，使用生产 `seatbeltProfile` 调用真实 `sandbox-exec` 读取，得到 `exit=0, readSentinel=true`。未读取真实密钥。

建议: 统一凭证存放边界与执行器资源声明；短期补齐所有正式凭证来源，长期明确文件读取能力，避免每增加一种配置来源就遗忘一处黑名单。保留假凭证路径的真实沙箱回归。

### A03: 服务恢复没有实例所有权前提

证据: [service.ts:180](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/service.ts:180)、[agent-runtime.ts:558](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/runtime/agent-runtime.ts:558)。

`createService()` 在绑定监听端口之前执行 `sweepInterrupted()`。恢复逻辑只检查当前实例的内存 running 表，无法识别另一个进程仍拥有的任务。常驻服务存在时执行默认 `npm run dev`，两个实例会使用相同的数据目录。

隔离复现: 在同一个隔离 Node 进程中构造两个真实 service 实例，ModelPort 使用受控等待替身。第一个 service 状态为 `isRunning=true / status=running / active_turn_id 有值`；仅构造第二个同目录 service 后，第一个仍在执行，但数据库已变为 `interrupted / active_turn_id=null`。第二个实例随后遇到 `EADDRINUSE`，也无法撤销先前修改。本探针没有运行两个独立 OS 进程或真实外部模型。

建议: 在迁移、恢复和任务写入之前取得数据目录独占锁，实例退出才释放；开发使用独立数据根。锁的范围必须是数据库归属，单靠端口探活不足以证明所有权。增加双实例争用测试。

### A04: 类型定义没有成为可执行的协议边界

证据: [server.ts:162](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/server.ts:162)、[server.ts:312](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/server.ts:312)、[server.ts:359](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/server.ts:359)。

消息仅经过 `JSON.parse(...) as ClientMessage`。解析成功不代表结构合法，随后 handler 直接访问字段和调用 runtime；部分异步分支只有 `.then`。协议类型提供编译期协作，却没有隔离不合法输入和运行时失败。

隔离复现: 连接临时服务，发送 JSON 文本 `null`，进程退出码为 1，错误为 `Cannot read properties of null (reading 'type')`。失败影响同一服务内的全部任务。

建议: 对外消息统一解码并验证字段，每个请求通过共同异常边界处理；错误必须返回对应请求，Promise 拒绝必须被收口。补充 null、数组、缺字段、字段类型错误及 handler 抛错测试。

### A05: 单 pending 槽把传输限制泄漏进业务层

证据: [messages.ts:59](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/messages.ts:59)、[agent-client.ts:408](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/agent-client.ts:408)、[agent-client.ts:642](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/agent-client.ts:642)、[App.tsx:440](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/App.tsx:440)。

请求和响应没有 requestId。客户端按响应种类保存单个 pending，后一次调用覆盖前一次调用；通用 ok/error 也无法确定属于哪个命令。App 已用注释要求项目列表和设置请求手工串行，说明底层限制已经决定上层交互方式。

隔离复现: 对真实 AgentClient 调用 `list('A')`、`list('B')`，先输入 A 响应，B 得到 A 的数据，A 永不结束；submit 收到 error 后，其 Promise 仍未结束。Node 客户端也保留同类单槽设计。

建议: 建立 requestId 与 `Map<requestId, pending>`，请求一律有成功、错误、超时、断线四种结算路径；任务事件仍按 taskId/seq 独立推送。将通用传输契约供两个客户端共用，测试乱序、重叠、断线和错误归属。

### A06: 上传与发送缺少贯穿异步过程的会话上下文

证据: [useComposerDraft.ts:81](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/app/useComposerDraft.ts:81)、[useComposerDraft.ts:107](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/app/useComposerDraft.ts:107)、[useAgent.ts:241](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/useAgent.ts:241)、[useWorkspace.ts:42](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/useWorkspace.ts:42)。

A 中的上传使用提交时捕获的 project/task；等待期间用户可切到 B。上传结束调用 send 时，send 从当前 ref 读取归属，已经变成 B。B 可接收新输入时，A 的文字和附件回执会发进 B；B 正在运行时则被服务端拒绝。原有 viewEpoch 检查只约束部分 UI 结果，没有约束命令的目的会话。

阅读器有相同根因: 异步 readAsset 结束后直接 setOpen，关闭或切会话不能使旧读取失效；App 又会将这个旧路径绑定为当前会话 activePath。

建议: 提交时创建不可变 `{ projectId, taskId, viewEpoch }`，上传和发送使用同一上下文；所有异步 UI 结果在提交前检查归属。增加上传中切会话、关阅读器后旧请求完成、相同文件名跨会话等真实组件场景。本项经过调用链确认，未执行原生 UI 端到端复现。

### A07: 新旧子代理路径拥有不同治理规则

证据: [agent-runtime.ts:653](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/runtime/agent-runtime.ts:653)、[agent-runtime.ts:721](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/runtime/agent-runtime.ts:721)、[core/spawn.ts:60](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/core/spawn.ts:60)、[coordinator.ts:142](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/subagent/coordinator.ts:142)。

生产工具集同时暴露旧 `spawn` 和新 `spawn_subagent`。旧路径通过 roles 直接运行内核并继承父 workspace/emit；新路径经过 Coordinator 登记、并发控制、禁用规则与写入条带隔离。旧 general-purpose 仍有可写、可执行工具，因此治理约束可以被换一个工具名绕开。

这也使列表、独立取消、子代理标识和预算统计的语义不统一。旧 worker 没有 subagent_id，预算折算会把它的模型步骤算作主步骤。

建议: 所有公开子代理命令都进入同一 Coordinator 与 Runner。统一注册、能力选择、工作区分配、计费及清理，并增加“两入口产生相同约束”的测试；完成迁移后收掉冗余入口。

### A08: 事务覆盖单条写入，没有覆盖业务状态转换

证据: [task-store.ts:189](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/storage/task-store.ts:189)、[task-store.ts:233](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/storage/task-store.ts:233)、[db.ts:25](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/storage/db.ts:25)、[db.ts:155](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/storage/db.ts:155)。

appendEvent 内部有事务，但 updateTaskStatus 先更新 tasks，再另起事务追加 status_change；beginTurn 同理。多个 schema ALTER 也各自提交，最后才写 user_version。数据库的单条写入可靠性没有扩展到应用所声明的“状态与事实源一致”。

故障注入结果:

- 内存数据库用触发器拒绝 event INSERT 后，updateTaskStatus 抛错，但 tasks.status 已是 running，最后事件仍为 queued。
- 同一条件下 beginTurn 抛错，active_turn_id 已写入，turn_start 事件为零。
- 构造“v10 DDL 已完成、版本号仍为 9”的迁移中间态，重启报 `duplicate column name: active_turn_id`。这模拟事务外 DDL 与版本写入之间中断后的持久状态，并非宣称做了真实断电试验。
- 另建 user_version=11 的数据库，当前 openDatabase 会直接改成 10，没有拒绝未来版本。

建议: 将任务转换所涉及的主表与事件写入纳入同一事务，提交成功后发布事件；每个 migration 的 DDL 与版本号原子提交，拒绝高于当前程序支持的数据库版本。加入写入失败回滚、迁移重试、旧程序打开新库测试。

### A09: 子代理直接写事件，绕开在线发布

证据: [coordinator.ts:157](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/subagent/coordinator.ts:157)、[coordinator.ts:318](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/subagent/coordinator.ts:318)、[event-hub.ts:84](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/runtime/event-hub.ts:84)。

EventHub 定义“先落库再广播”，但 Coordinator 直接调用 TaskStore.appendEvent。订阅者不监听数据库，因此这些事件只能通过后续回放看见。UI 又确实消费 subagent_started/completed，在线与重入后的界面不同。

隔离复现: 对临时 runtime 订阅任务，再执行 registerSpawn 和 complete；数据库出现 started/completed/reminder，实时订阅结果为 `[]`。

建议: 收敛 durable event 的提交和发布出口，让生产者提交事件意图；禁止需要实时可见的生产者绕过发布路径。验收应比较同一事件序列的 live 与 replay 结果。

### A10: 任务初始化失败逃出清理范围

证据: [agent-runtime.ts:643](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/runtime/agent-runtime.ts:643)、[agent-runtime.ts:726](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/runtime/agent-runtime.ts:726)、[agent-runtime.ts:773](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/runtime/agent-runtime.ts:773)。

### A11: 连接状态与执行状态被局部 UI 操作覆盖

证据: [useAgent.ts:197](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/useAgent.ts:197)、[useAgent.ts:204](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/useAgent.ts:204)、[useAgent.ts:214](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/useAgent.ts:214)。

任意 reply/error 将 running 设 false，status_change 却不把 running 恢复为 true；断线直接 false，重连只 subscribe。进入一个旧轮已完成、新轮仍运行的会话时，历史 reply 会覆盖选择会话时传入的运行态。运行中掉线后重新连上，也无法恢复 Stop 和禁重复发送状态。

建议: 执行状态成为生命周期事件的统一投影，连接状态单独建模；订阅提供状态快照及对应序号，重放不能让较旧的终态覆盖当前 turn。增加多轮会话回放和断线重连测试。

### A12: 自动安装规则覆盖用户常驻偏好

证据: [SettingsModal.tsx:194](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/components/SettingsModal.tsx:194)、[launchd.ts:209](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/launchd.ts:209)、[main.rs:366](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src-tauri/src/main.rs:366)、[main.rs:531](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src-tauri/src/main.rs:531)。

## 条件性风险与已知交付边界

### 公网 demo 没有可信租户身份

证据: [server.ts:137](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/server.ts:137)、[server.ts:145](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/server.ts:145)、[server.ts:359](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/server.ts:359)。

demo 的 ownsTask 比较消息自己声明的 projectId 与任务归属，无法证明调用者身份；task_updated 又向所有连接发送完整任务元数据。资产接口也未从受信任身份派生访问范围。若公开部署为多人服务，应按 P1 处理；本轮没有核实存在公网部署。

### 桌面包仍是开发机交付形态

## 架构判断

保留现有两包结构是合理的。核心 `runAgent` 依赖端口与纯类型，能在无 WebView 环境下测试；工具真源 registry、独立 ModelPort、事件序号与回放也提供了可继续治理的基础。

对 202 个 TS/TSX 源文件做静态相对路径运行时 import/export 图分析，没有发现运行时循环依赖。该检查排除了 type-only 导入，不代表检查了动态 import、Rust 调用或所有逻辑耦合。

主要压力在编排边界: App 有 32 条静态本地运行时依赖，AgentRuntime 有 31 条；快照中 App 833 行、AgentRuntime 805 行、浏览器客户端 788 行、styles.css 2744 行。行数本身不是缺陷证明，但两处编排对象确实分别承担了连接、会话、上传/资产，以及执行、skills、子代理、工作区等多个变化理由。

更深的共同根因是所有权不明确:

- 服务不知道哪个进程拥有持久状态。
- 协议不知道响应属于哪个请求。
- 异步命令不知道自己属于哪个会话。
- 事件生产者不知道谁负责提交与发布。
- UI 不知道执行状态应以哪个生命周期事实为准。

应先把这些所有权落实为接口与不变式，再沿稳定边界拆编排代码。仅按行数切文件，会保留同样的故障机制。

## 建议治理顺序

1. **收紧信任边界**: A01/A02/A04，默认鉴权、凭证读取边界、协议解码与异常收口。公网 demo 在身份模型完成前保持非公开单用户用途。
2. **保证持久执行可靠**: A03/A08/A10，数据目录独占、迁移与状态事务、完整执行生命周期。
3. **统一通信和归属**: A05/A06，requestId、请求结算、不变会话上下文；同步两类客户端和 UI 调用点。
4. **统一事实与执行入口**: A07/A09/A11，子代理单入口、事件单出口、UI 生命周期投影。
5. **建立持续验收**: A12/A13，持久常驻意图与统一门禁；以上每阶段先补能证伪问题的测试。最后依照这些边界拆 App 和 AgentRuntime，并更新对应 L2/L3。

可采用的小范围目标结构: protocol 负责 decode/request/response；应用服务负责带归属的命令；TaskStore 负责原子状态转换；事件发布层负责已提交事件；Runner 负责一次执行的资源生命周期。实现中优先复用现有模块，新增抽象必须实际消除重复的所有权判断。
