## 0. 结论

Lumen 的跳动不是单个 CSS 动画或某一次 `scrollToBottom` 导致,而是一个**语义锚点不连续**的问题:

> 回答仍在增长和定稿时,内容高度、Markdown 结构、Mermaid 几何、消息 ID 与 DOM 外壳都会变化;但滚动系统没有一个能跨越这些变化、继续代表“用户正在看的内容点”的稳定锚点。

现象必须按滚动状态分成两条链:

| 状态 | 主链 | 视觉结果 |
|---|---|---|
| sticky:用户仍在追最新 | 每次 token/RO 都重置 140ms 静默窗,静默后整段追底 | 内容先积累、视口停住、随后突然跳到底;间歇重复形成锯齿 |
| manual:用户已离底阅读 | 自定义锚点只记录整条消息顶部;消息内部重排或身份替换无法补偿 | 眼前段落/图节点被推走,即使 `scrollTop` 没被主动修改 |

截图中的“回到最新”箭头可见,所以该截图对应 **manual 链**。因此不能用“sticky 抢权”单独解释现场。

本次最确定的三个结构缺陷是:

1. token 增长与异步媒体布局共用同一个 140ms debounce 策略;
2. manual 锚点粒度停留在“消息”,无法表达超长消息内部的阅读位置;
3. 流式消息与终稿使用不同事件 ID 和不同 DOM 外壳,使锚点与 React 子树在定稿时失去连续性。

Mermaid 多阶段落位与整篇 Markdown 重解析是高度变化的主要来源;`overflow-anchor:none` 使浏览器不再提供兜底补偿。

## 2. 第一性原理

### 2.1 稳定视口的唯一合同

设用户正在看的语义内容点为 `P`,它在滚动容器中的文档坐标为 `docY(P)`,滚动位置为 `scrollTop`:

```text
screenY(P) = docY(P) - scrollTop
```

页面稳定的含义不是“`scrollTop` 不变”,而是:

```text
delta screenY(P) = 0
```

若 `P` 上方内容增高 400px,`docY(P)` 增加 400px,滚动系统就必须同步让 `scrollTop` 增加 400px。反之,如果系统只观察整条消息顶部,而 `P` 位于消息内部,它可能看不见这 400px。

### 2.2 跳动的完备来源

在没有用户手势时,可见内容改变位置只有四类来源:

| 类别 | 机制 | Lumen 实例 |
|---|---|---|
| S | 程序修改 `scrollTop` | sticky follow、manual restore、pin |
| L | DOM 布局改变 `docY(P)` | Markdown 重排、过程块收合、Mermaid 增高/塌缩 |
| A | 浏览器原生 scroll anchoring | 当前被 `.messages { overflow-anchor:none }` 关闭 |
| I | 目标身份消失或替换 | 流式 ID → model_step ID;`.bubble` → `.msg-group` |

GPU 绘制慢会造成掉帧,但不能单独解释几何位置改变。要解释“跳到另一页”,最终仍必须落到 S/L/A/I 之一。

## 4. sticky 链:140ms 产生锯齿式追底

### 4.1 代码路径

`packages/ui-client/src/scroll/useStickToBottom.ts`:

- `followSettleMs` 默认 140ms(`:26-27`,`:116`);
- 每次 ResizeObserver 增高都会清除旧 timer,再创建新 timer(`:312-347`);
- 每次 `contentKey` 改变也走同一个 140ms timer(`:540-552`);
- timer 到期后才执行 `runFollowNow(false)` → `scrollToBottom('auto')`。

而 `text_delta` 每次都增长最后一条消息正文,因此 token 更新和内容 RO 会共同续期这扇静默窗。

### 4.2 为什么它必然阶梯化

假设 token 到达间隔依次为 30ms、40ms、50ms、190ms:

```text
token 1 ─┐
token 2 ─┼─ timer 不断重置,内容长了但不 follow
token 3 ─┘
         140ms 静默
              └─ 一次性 scrollToBottom
```

只要模型输出存在自然停顿,视口就会在每次停顿后跳一次。连续 token 越密,单次积累的位移反而越大。

### 4.3 设计错误

140ms 的注释目标是“合并 Mermaid 逐个落位”,但实现没有事件类型,无法区分:

- 单调、频繁、应该按帧跟随的文字增长;
- 稀疏、非单调、需要稳定盒模型的异步媒体布局。

这是把两个不同控制问题压进一个时间常数。调成 50ms 只会改变跳动频率,调成 300ms 只会改变每次跳动幅度。

**判定:确定性主因(sticky 场景)。**

## 5. manual 链:消息级锚点无法稳定消息内部

### 5.1 当前锚点公式

`packages/ui-client/src/scroll/scrollMsgAnchor.ts` 选择视口内第一条 `[id^="msg-"]` 消息,保存:

```text
anchor = { messageId, messageTop - containerTop }
```

恢复时只比较同一消息元素的新旧顶部:

```text
delta = newMessageTop - oldMessageTop
scrollTop += delta
```

### 5.2 超长消息的盲区

当一条消息比视口高很多时,用户可能正在读消息内部第 40 段。此时:

- 消息元素顶部在视口上方数千像素;
- Mermaid 或 Markdown 在第 20 段发生高度变化;
- 第 40 段被推走;
- 但整条消息元素的顶部没有变化。

于是恢复算法得到 `delta=0`,它在数学上正确恢复了“消息顶部”,却没有恢复用户真正看的第 40 段。

截图正是这个结构:一条 7902 字回答内部的大图占据视口,整条消息顶部早已失去阅读语义。

### 5.3 为什么 `overflow-anchor:none` 放大了问题

`packages/ui-client/src/styles.css:1122-1129` 固定关闭浏览器原生滚动锚定。这样可以避免过去浏览器自行选择错误锚点,但也意味着:

> 自定义锚点一旦粒度不足,系统没有第二层补偿。

关闭原生 anchoring 本身不是根因;“关闭后没有等价能力的自定义语义锚点”才是根因。

**判定:确定性主因(manual 超长消息场景)。**

## 6. 定稿身份断裂:旧锚点会直接消失

### 6.1 消息 ID 来自传输事件,不是 turn 内稳定实体

`packages/ui-client/src/chat/reduce.ts`:

- 第一个 `text_delta` 创建流式消息时使用 `id:event.id`(`:390-410`);
- 后续 delta 复用该消息;
- `model_step` 定稿时用 `finishAssistant(event.id, content, ...)` 替换该消息(`:451-465`)。

`text_delta` 和 `model_step` 是不同事件,因此定稿通常更换消息 ID。

### 6.2 React DOM 也更换外壳

`packages/ui-client/src/app/ChatTranscript.tsx:129-160`:

- provisional/streaming 分支:`key=it.id` 的单个 `.bubble`;
- final 分支:`key=it.id` 的 `.msg-group`,内部再放 `.bubble` 和操作栏。

定稿同时发生:

```text
旧 key 消失
→ React 卸载流式消息子树
→ 新 key 挂载终稿子树
→ msg-* 锚点 ID 改变
→ 旧 anchor 无法 restore
```

如果同一时刻 `stripProcessItems` 移除了过程块,视口上方还会发生额外塌缩。即使新的 DOM 最终视觉内容相同,身份不连续已经让滚动层失去参照物。

这比“某个 inline callback 可能造成 remount”更确定:ID 与外壳切换直接写在归约和渲染分支里,不依赖 ReactMarkdown 内部实现。

**判定:确定性主因(定稿窗口)。**

## 7. 高度震源

### 7.1 Mermaid 首次渲染的高度相变

流式期间,`Markdown.tsx:69-81` 把 Mermaid 保持为源码 `<pre>`。定稿后改为 `MermaidBlock`,首次渲染依次经过:

```text
源码 pre
→ MermaidBlock pending(正在绘制,min-height 3.5rem)
→ 异步 mermaid.render 产生原始 SVG
→ 下一帧 measureSvgHeight/tightenSvgInk 改 viewBox 和固有尺寸
→ 写入 lockMinH 缓存
```

对应代码:

- pending / 清空 SVG:`MermaidBlock.tsx:222-225`;
- 异步 import、parse、render:`:226-271`;
- 下一帧测量与收紧:`:272-276`;
- pending / SVG DOM 分支:`:485-536`;
- pending 最低高度:`styles.css:2332-2339`。

`lockMinH` 依赖已有缓存。首次渲染缓存尚未持有最终高度,所以它只能保护后续 remount,不能消除第一次 `pre → pending → SVG → tighten`。

单张 Mermaid 已足以产生多次 RO 和多次视觉位移。

### 7.2 每个 delta 重解析完整 Markdown

`text_delta` 每次执行:

```text
last.content + text
→ 新 ChatItem 数组
→ ChatTranscript 重渲染
→ AssistantContent 重新分段
→ ReactMarkdown 重新解析整条累积字符串
```

流式模式虽然关闭了 KaTeX 并不渲染 Mermaid SVG,但 GFM 与代码高亮仍运行。未闭合 fence、列表、表格或强调标记可能改变尾部结构;完整重解析还会放大主线程负载。

这一项对“掉帧/顿挫”是确定放大器;它是否会移动截图所在的较早内容,取决于具体 Markdown 结构,需要逐帧 DOM trace 判断贡献比例。

### 7.3 过程块收合与 callback 身份

过程块在终局被 `stripProcessItems` 移除,会与 Mermaid 落图叠加高度变化。

终稿的 `onRepairMermaid` 采用内联函数,可能使 Markdown components 身份不稳定。但是否因此额外卸载 MermaidBlock 需要 React Profiler 证明。本报告将其列为候选放大项,不列为已证实主因。

## 8. 完整事件时间线

### 8.1 sticky 追更

```text
text_delta
→ content 字符串增长
→ 完整 Markdown 重解析
→ contentKey 变化 + ResizeObserver
→ 两路都重置 140ms timer
→ 视口暂时不动,内容继续积累
→ 模型短暂停顿
→ timer 到期
→ scrollTop = scrollHeight
→ 视口突然跳到当时的底部
```

### 8.2 manual 阅读

```text
用户上滑
→ sticky=false,下箭头出现
→ captureVisibleMsgAnchor 捕获整条消息顶部
→ 消息内部 Markdown/Mermaid 重排
→ 整条消息顶部可能不动
→ restoreMsgAnchor 得到 delta=0
→ 眼前内容移动,算法却认为稳定
```

### 8.3 model_step 定稿

```text
流式消息(text_delta event id,单 bubble,源码 pre)
→ model_step
→ process 块卸下
→ 消息 id 改为 model_step event id
→ DOM 改为 msg-group
→ 旧锚点与旧 React 子树消失
→ Mermaid pending
→ 原始 SVG
→ rAF tighten
→ 每个阶段触发新的内容高度
```

三条时间线可以在同一次回答中交叠,因此用户会感觉页面“不断换位置”,而不是只在结束时跳一次。

## 9. 邻居产品对照

### 9.1 OpenWork

路径:`/Users/zihao/projects/openwork/apps/app/src/react-app/domains/session/surface/`

`scroll-controller.ts:260-289` 的 ResizeObserver 只在以下条件同时满足时立即跟随:

```text
content 真正增高
AND session 仍为 stickyBottom
AND 最近没有用户手势
```

它没有用 140ms 静默窗处理普通增长。manual 状态会恢复 `overflowAnchor:auto`(`:96-100`),并按 session 保存 `scrollTop` 与顶部裁切消息。

`components/markdown/markdown.tsx:309-315` 对已完成 MarkdownBlock 使用 `memo`,旧回答不会随当前 token 重解析。

可借鉴的是“增长即时跟随 + 用户意图在执行时检查 + 已完成消息隔离”,不是照搬它的全部滚动代码。

### 9.2 OpenSquilla

`opensquilla-webui/src/composables/chat/useChatStream.ts`:

- 流式事件先标 dirty;
- 用 requestAnimationFrame 合并提交;
- 重型 Markdown 解析最短间隔 33ms(`:215-227`,`:426-480`);
- 未闭合 fence 只在渲染副本中临时闭合,原始文本不变(`:483-490`);
- 流式期关闭语法高亮,终稿一次性恢复。

`views/ChatView.vue:3088-3096` 在 Vue `nextTick` 真正执行滚动时再次检查 `autoScroll`,已经发生的用户上滑可以取消排队中的自动滚动。

它没有直接证明 Mermaid 问题已经解决,但显著减少了进入 DOM 的无意义中间状态。

### 9.3 OpenPencil 与 old_lumen

- OpenPencil `src/components/ChatPanel.vue:61-67` 深度 watch messages,每次 smooth `scrollIntoView`;
- old_lumen `AiPanel.tsx:55-57` 同样在 messages 变化时 smooth 滚到底部。

这种方案代码少,适合短消息和简单 Markdown;它不区分 manual 阅读意图。对 Lumen 的超长回答、工具过程和异步图表,照搬会把“跳动”变成持续抢滚动。

### 9.4 对照结论

稳定产品依靠的不是一个 CSS 属性,而是三条系统不变量:

1. UI 业务实体在流式到终稿之间保持身份连续;
2. 高频 token 先按帧合并,再提交 DOM;
3. 自动滚动执行前读取最新用户意图,而非相信排队时的旧状态。

Lumen 当前三条都不完整。

```text
timestamp
sticky/manual
scrollTop / scrollHeight / contentHeight
当前可见语义节点 rect
消息 id / React mount generation
Mermaid phase(pre/pending/svg/tightened)
最近手势时间
触发来源(contentKey/RO/model_step)
```

| 实验 | 操作 | 本报告预期 |
|---|---|---|
| T1 纯散文 sticky | 长纯文字,不含列表/围栏/图 | `scrollTop` 在 token 停顿后呈 140ms 阶梯;证实 sticky 独立链 |
| T2 纯散文 manual | 输出中上滑阅读已稳定前缀 | 基本稳定;若仍大跳,需寻找过程块或其它 S 写手 |
| T3 单 Mermaid manual | 图定稿前上滑到消息中部 | 消息顶 delta 接近 0,可见子节点 rect 明显变化;证实锚点粒度错误 |
| T4 定稿身份 | 记录 msg id 与 mount/unmount | text_delta id 消失,model_step id 新建;证实身份断裂 |
| T5 followSettle 对照 | 仅实验构建分别用 0/33/140ms | 140ms 跳幅最大;0/33ms 改变 sticky 阶梯但不修 manual Mermaid |
| T6 Mermaid 阶段 | 记录 block 高度与 phase | 首次 render 至少出现 pending 与 SVG 高度变化;tighten 是否再变由图决定 |

其中 T1 与 T3 是最关键的正交实验:分别隔离 sticky 写手和 manual 布局锚点。

## 13. 后续修复边界(本报告未实施)

按依赖顺序,而不是按文件顺序:

1. **稳定身份**:同一 assistant turn 从首个 delta 到终稿使用同一个 UI message id 与稳定外壳;

## 14. 品味自检

### 可消除的特殊情况

当前滚动核已经积累 sticky/manual、gesture window、collapse guard、programmatic guard、RO、contentKey 与 settle timer。继续增加分支是在下游补偿上游不稳定布局。

应优先消除:

- 流式/终稿两个身份;
- token/media 两种变化共用一个 timer;
- 已稳定 Markdown 随尾部 token 重解析;
- 首次 Mermaid 中间态进入主滚动流。

### 不必要的抽象

“消息顶部就是阅读锚点”在短气泡里简单有效,但对 7902 字长消息已经是错误抽象。问题不在公式写错,而在对象选错。

### 最小正确设计

让同一语义实体保持同一身份,让稳定内容不再变化,然后滚动只需要回答一个问题:

```text
用户是否仍选择追随最新内容?
```

当滚动核还必须理解 Mermaid、process collapse 和 Markdown fence 时,职责边界已经反了。
