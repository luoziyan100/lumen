## 0. 工作结论(采用)

独立复核整体更严谨:按 sticky / manual 拆链,抓住了 140ms 锯齿和消息身份断裂,并把 Markdown / Mermaid / callback 的证据等级压回合理位置。

内容层报告的**源码事实大部分为真**,但主因排序和若干视觉因果写得过满;§15 已承认 sticky 140ms,正文 §0/§7 未改,内部自相矛盾。它是高价值假设清单,不能单独当最终定因。

**合并结论:**

> **sticky 跳动**主要来自 140ms debounce:token 与 ResizeObserver 共用一扇静默窗,连续输出不断续期,停顿后一次性 `scrollTop = scrollHeight`。
>
> **截图中的 manual 跳动**主要来自三条并列机制:(1) 超长消息内部布局变化(含中间未闭合 fence 把后续正文吞进 code、闭合时再吐出;以及 Mermaid `pending → SVG`);(2) 锚点只记录整条消息顶部,钉不住气泡内部阅读点;(3) 流式 `text_delta` id → 终稿 `model_step` id,同时 `.bubble` → `.msg-group`,旧锚点与 React 子树断开。
>
> 全量 `ReactMarkdown` 是确定的主线程/掉帧放大器。Mermaid 首次落位是确定的高度源。**「三次可见跳动」和各机制贡献比例尚未用浏览器 trace 量化**,不能标成已证实。
>
> 不是整套前端重做,也不是再叠一套 sticky 状态机。

截图判定(两边同意,已核对):「回到最新」↓ 可见 ⇒ `pinned=false` ⇒ **manual 读图**,不能用 sticky 抢权解释这张图。L92:7902 字、1 个 mermaid fence,节点文案与截图一致。

## 1. 独立复核 6 条元裁定 — 核验结果

### 1. 内容层把 A 层降为放大器,sticky 不成立 — **属实**

代码:`useStickToBottom.ts` 的 `followSettleMs` 默认 140ms;增高走 ResizeObserver 清 timer 再设; `App.tsx` 的 `stickContentKey` 含 `last.content.length`,每个 delta 也走同一 timer。停顿后 `runFollowNow` → `scrollTop = scrollHeight`。

这是 sticky 场景的**直接跳动机制**,不是旁观放大。OpenWork 的 RO 在 sticky 且无手势时立即 follow,没有这扇窗。

截图走 manual,140ms 在 `sticky===false` 时不跑。正确写法是**两条链**,不要争一个总主因。

内容层 §15 承认了,§0「滚动层只是放大器」与 §7 表「A 放大(非震源)」未改 — 内部矛盾成立。

### 2. 「未闭合 mermaid 闭合时裂开重排」不符合解析器 — **半对;测的不是同一个对象**

独立复核用 `react-markdown@10.1.0 + remark-gfm` 测「同一 Mermaid fence」未闭 vs 已闭:

```text
<pre><code class="language-mermaid">…</code></pre>  IDENTICAL=true
```

本轮用仓库 `mdast-util-from-markdown` + `micromark-extension-gfm` 复跑:

| 样本 | 结果 |
|---|---|
| 只有围栏,不闭 vs 闭 | mermaid `code` 节点 lang+value **IDENTICAL=true**(复核测的就是这个) |
| 围栏后面还有正文/标题 | 未闭合:后续全部吞进同一个 `code`;闭合:裂成 `code + paragraph + heading` |

内容层写的「一块超长代码裂成图 + 后面的字」指的是**围栏后面的文档**,不是 mermaid 那个 `<pre>` 换标签。L92 的图在 7902 字**中间**,后面还有大段正文。流式时 fence 一开,后续 token 先进 code;闭合瞬间那些字回到块级文档。这是解析器事实。

因此:

- 「围栏节点自身 HTML 不变」→ 复核属实
- 「因此裂开重排不成立」→ **不属实**(否掉了另一个对象)
- 列表/表格:本轮实测前面的段落节点类型不变,变的是尾巴。内容层「已经画出来的前面几段重排」过了
- 「尚未证明多屏跳动」对列表/强调的微变过稳;对 L92 这种中间开围栏,闭合时放出后面几千字,**足以改变多屏几何**,只是还没有逐帧录到

全量解析作为性能/掉帧放大器 — 两边同意,属实。

### 3. 「三次可见跳动」写过头 — **属实**

`MermaidBlock.tsx`: `setPending(true)` → 异步 `mermaid.render` → 同一次续里 `setSvg` + `setPending(false)` → `requestAnimationFrame(tightenSvgInk)`。

rAF 在下一次绘制前执行。虚高 SVG 与 tighten 很可能落在同一帧。确定可见的是:

- `pending`(css `min-height: 3.5rem`)持续异步渲染的几百 ms
- 然后接近整屏的 SVG

第二、第三个「可见落点」需要逐帧 trace,不能标 V2,也不能写「必跳 2–3 次」。

### 4. 过程卡与 Mermaid「同一窗口同时收合」无源码证据 — **属实,时序更分得开**

`core/loop.ts`:无工具时先 `emit(model_step)` 再立刻 `emit(reply)`。

- `model_step`: `stripProcessItems` + `finishAssistant(event.id)`(换 id);此时 UI `running` 仍 true。`ChatTranscript` 最后一条不在 `finalAssistantIds`,`isStreaming` 仍 true,mermaid **仍是源码 pre**
- `reply`: `useAgent` `setRunning(false)`,才切 SVG / `.msg-group`

两帧相邻,不是同一 React commit。内容层标 V2「常同时」是时序猜测。

另:`ProcessRow` 在 `running=false` 时 CurtainFold 收合,与 `stripProcessItems` 卸 DOM 是两件事。终局过程块已被 strip,CurtainFold 那条在终局路径上往往已经没了。

### 5. Hermes「单一 scrollTop 写手 / 绝不直接碰」— **方向对,行号略滑**

独立复核指 `list.tsx:183`。该行是 `useAuiEvent('thread.runStart', () => scrollToBottom())`,走库 API。

真直接写 `el.scrollTop` 的是:

- 会话切换 `useLayoutEffect` `:199`(以及 settle 循环 `:216`)
- prepend 恢复 `:247`

Hermes 注释里的「单写手」是指**流式期不要让虚拟列表/预算渲染跟 `use-stick-to-bottom` 抢**。内容层压成「不许碰 scrollTop」是错的。

仍为真、可借鉴:流式正文不进根组件、~33ms commit、tail-bounded remend、用户问句 `position: sticky`。

### 6. 「ChatGPT / Claude / Cursor / Hermes 都钉本轮开头」— **属实,证据不够**

只有 Hermes 有源码。另外三家没有本机源码或现场 trace,是 V4 类比,不该写成已验证的行业同构。产品选择「追更钉开头」仍标可选,不是这张截图的最小修复。

## 3. 仍保留的歧义(修代码时不要假装已闭合)

1. **sticky 纯散文**在 140ms 阶梯下,主观上算「跳动」还是「攒一截再跟上」— 要 T1 才能量。机制本身确定。
2. **围栏闭合放出后续正文**在 L92 上有多大视口位移 — 解析器机制确定,像素幅度未录。
3. **tighten 是否单独成帧** — 见 §1.3。
4. **`onRepairMermaid` remount 是否真实发生** — 待 Profiler。
5. **意图 A 要不要改成钉本轮开头** — 产品规格,不是这张图的最小修复;两边都未证明为必需。

## 5. 修复顺序(按依赖,不是按文件)

身份断裂、140ms 混用 timer、`pending→SVG` 已是 V2,**不必等 trace 才动这三件**。trace 用来量比例和 tighten 是否成帧。

1. **稳定身份** — 同一 assistant turn 从首个 delta 到终稿用同一个 UI message id;流式/终稿不要换根节点类型(不要 `.bubble` ↔ `.msg-group` 换 key 树)。
2. **拆分调度** — 普通 token 按帧合并并单调跟随;媒体/公式/图不走 140ms 那扇窗。
3. **一次落图** — Mermaid 离屏 `render` + `tighten` 后再进 `.messages-content`,或首帧占位等于最终盒。这才是 R11 P1。
4. **稳定前缀** — 已闭合 Markdown 块不随尾巴重建;未闭合 fence 只存在于尾部渲染副本(opensquilla 临时补闭 / hermes remend-tail 一类)。顺带消化 §1.2 的「中间围栏吞正文」。
5. **语义锚点**(可后做) — manual 锚到视口内稳定块/段落/Range,不是只锚消息顶。7902 字时消息顶已无阅读语义。
6. **浏览器集成测试** — 覆盖独立复核 T1(纯散文 sticky 阶梯)与 T3(单 mermaid manual,消息顶 delta≈0 但子节点 rect 变)。

不先做:钉用户问句的产品合同(内容层 §8.4)。1–4 之后用实验决定要不要改 `chat-scroll-ux.md` 意图 A。

## 6. 代码坏味道(给实现者)

- 一个 timer 混合高频单调增高(token)与稀疏非单调布局(图)
- UI 实体身份绑传输事件 UUID,ephemeral 与 durable 不是同一个 id
- manual 锚点粒度停留在「消息」,超长气泡里对象选错
- `ChatTranscript` 用 `running` 把最后一条一直当 streaming,mermaid 要到 `reply` 才画,和 `model_step` 卸过程错开
