## 0. 最终裁定

《对话列跳动对拍结论》的**底层源码事实大多正确**,但它仍不是可直接交给实现的最终定因。它还有四个关键跨越:

1. 用截图时的 manual 状态,外推整段「不断跳动」的时序;
2. 用静态 Markdown 样本,替代 append-only token 流的因果顺序;
3. 将 Mermaid 软件状态序列,部分写成肉眼可见落点;
4. 忽略真实会话中过程卡可反复收起、复活和移位,却直接给出修复顺序。

当前可以确定的是**三条独立链**,不是一个「截图总主因」:

| 链 | 确定机制 | 未决项 |
|---|---|---|
| sticky 追更 | token/RO 反复续期 140ms timer,停顿后一次追底 | 用户报告的跳动帧有多少发生在 sticky |
| manual 阅读 | 锚点只记整条消息顶;ID/外壳定稿断裂 | 具体哪次内部布局变化产生了主观大跳 |
| 过程卡 | 工具完成时收起,下一批工具又复活/移到末尾,终局再卸载 | 在这条多工具真实会话中的跳幅占比 |

## 2. 关键问题(按严重程度)

### 2.1 [P0] 静态 Markdown 样本不等于真实 token 时序

《对拍结论》§1.2 声称:

> L92 的图在回答中间;流式时 fence 一开,后续 token 先进 code;闭合瞬间这些字回到块级文档,足以改变多屏几何。

这个静态 AST 描述对人工构造的「未闭 fence + 普通正文」样本成立,但不符合真实 append-only 流的时间顺序。

设最终文本为:

```text
prefix
open fence
mermaid source
close fence
trailing prose
```

对任何只在末尾追加的 `text_delta` 流:

1. `close fence` 的字符必然先于 `trailing prose` 到达;
2. 在闭 fence 到达前,DOM 中存在的只是 Mermaid 源码的已到达前缀;
3. 在闭 fence 到达后,新到达的 trailing prose 从出生起就在 code 外;
4. 不存在「几千字正文已在 code 内显示,后来闭 fence 插入到它们前面」的过程。

当前项目依赖 `react-markdown@10.1.0 + remark-gfm@4.0.1` 实测还表明,同一 Mermaid 源码前缀在 fence 未闭与刚闭后生成相同节点:

```html
<pre><code class="language-mermaid">...</code></pre>
```

只有两种情况可能产生「旧文字被重新分块」:

- delta 不是 append-only,而是在已有文本中间插入字符;
- `model_step` 用一个与已累积 delta 不同的整包 content 替换流式内容。

本仓 `text_delta` 归约明确执行 `last.content + text`(`chat/reduce.ts:396-401`),所以第一种不存在。第二种属于终稿整包替换/ID 断裂链,不是普通 fence 闭合链。

**裁定:**《对拍结论》§1.2 的 parser 静态结果为真,但对真实 token 时序的因果解释为假。它不能用来证明 L92 在闭围栏时吐出几千字已显示正文。

### 2.2 [P0] 过程卡不只是终局的一次叠加

当前用户面归约会反复执行:

```text
tool_call
→ appendProcessStep(... running=true)
→ ProcessRow 展开,过程块移到列表末尾

tool_result(当前全部完成)
→ running=false
→ ProcessRow setOpen(false)
→ CurtainFold 收起

下一批 tool_call
→ running=true
→ 再展开/再移位

final model_step/reply/status_change
→ stripProcessItems
→ 整块卸载
```

源码证据:

- `chat/reduce.ts:304-326`:复活现有过程块,设 `running=true`,并移到末尾;
- `chat/reduce.ts:633-659`:所有当前步骤完成后设 `running=false`;
- `components/ProcessRow.tsx:16-22`:`running` 改变时自动展开/收起;
- `chat/reduce.ts:278-283,447-465`:终局卸载过程块。

现场会话在终稿前确实有多批工具:

```text
L83       tool_result(run_code)
L84       assistant(tool_calls=5)
L85–L89  5 个 tool_result(read_file)
L90       assistant(tool_calls=1)
L91       tool_result(todo_write)
L92       assistant(final,7902 chars)
```

**裁定:**「过程块是叠加,不是现场主因」没有被证明。在解释「生成期不断跳」时,这是必须与 sticky/manual 并列量化的第三条链。

### 2.3 [P1] 截图时 manual 不能代表跳动全程 manual

下箭头只证明截屏当时 `pinned=false`。它不记录:

- 用户何时从 sticky 转为 manual;
- 主观「跳动」发生在上滑前还是上滑后;
- 跳动时的 `scrollTop/contentHeight/process/Mermaid` 状态。

若跳动发生帧中 `stickyRef.current===false`,140ms follow 确实不执行。但只能据此排除「140ms 单独解释截屏当时的 manual 位移」,不能排除它对整次用户报告的贡献。

### 2.4 [P1] Mermaid 状态序列不等于三次可见落位

代码确定经过:

```text
source pre
→ pending
→ setSvg(raw SVG)
→ requestAnimationFrame
→ tightenSvgInk
```

但 rAF 通常在下一次绘制前执行。原始 SVG 可能尚未单独 paint,就已经被 tighten。

**裁定:**`pre/pending→最终 SVG` 的高度相变确定;「必然肉眼看见 2–3 次跳」不成立。必须用 paint/filmstrip trace,不能只数 React state。

### 2.5 [P1] ID 断裂确定 remount,不单独证明位移

ID 和根元素类型同时变化,足以证明旧子树卸载、新子树挂载,并使旧 `msg-*` 锚点消失。这是比内联 `onRepairMermaid` 更强的结构证据。

但 remount 要造成可见位移,还需至少一个条件:

- 新旧子树几何不同;
- 新树经过 pending/异步媒体状态;
- 布局变化时旧锚点恢复失败。

**裁定:**身份断裂是确定缺陷和高价值修复候选;其对跳幅的独立贡献仍待 trace。

### 2.6 [P1] 「同一 assistant turn 用同一 UI id」语义过宽

一个 turn 内可以有多次:

```text
text_delta
→ model_step(tool calls)
→ provisional 旁白降级为 Thought
→ tool_result
→ 新 text_delta
→ final model_step
```

若整个 turn 强行共用一个 UI ID,可能混淆 Thought、工具前旁白与最终回答。更精确的合同应是:

> 当一个无工具的 `model_step` 正在封口当前 provisional assistant 时,继承该 provisional 消息的 UI ID,并保持根 DOM 外壳类型不变。

测试中的 `d1→m1` 只证明现行行为,修复时应同步改写测试合同。

### 2.7 [P2] 「已排除旧 App 分叉」是高概率判断,不是形式证明

当前 HEAD 提交时间为 `2026-08-21 22:28:47`,`/Applications/Lumen.app` 二进制时间为 `22:28:37`,只早 10 秒;相关 UI 文件此后也没有新提交。这强烈支持「安装 App 来自当时工作树」。

但 App 内无 commit hash,现存 bundle 与安装 App 的二进制 hash 也不相同。所以旧包不是优先解释,但不能写成已形式排除。

### 2.8 [P2] I 是否算第四种来源不影响决策

从像素物理看,位移最终落到 `scrollTop`、DOM 布局或 SVG 几何;从软件诊断看,「用户正在看的语义对象被替换」值得单列为 I。两种分类都自洽,不应继续消耗对拍精力。

## 3. 对《对拍结论》修复顺序的裁定

对拍结论给出:

```text
1. 稳定整个 assistant turn 的 UI id/根外壳
2. 拆分 token 与媒体调度
3. Mermaid 一次落图
4. Markdown 稳定前缀
5. manual 语义锚点
```

其中身份连续和 Mermaid 一次提交是高价值候选,但整体顺序仍不能称为「已证」:

1. ID 应稳定当前被封口的 provisional assistant,不是整轮所有助手语义;
2. 稳定 ID 必须与稳定根元素类型同时落地;
3. Mermaid 「离屏」必须在可测量但不进主流的 DOM host 中完成 `getBBox/tighten`;`display:none` 不能保证可测;
4. Markdown 稳定前缀能降低开销,但不能用错误的 fence 时序把它升为已证几何主因;
5. 真实会话有多批工具,过程卡链不能从实施顺序中消失;
6. 用户原问题是泛化的「模型回答时不断跳」,不只是定稿读图,sticky 140ms 不能无限后置;
7. manual 细锚点是对晚到图片、widget、字体与任何气泡内布局的通用合同,不只是 Mermaid 补丁。

**结论:**不反对先做「稳定 provisional 身份 + 稳定外壳」的小实验,也不反对 Mermaid 一次提交;但在没有过程卡与统一时序 trace 前,不能承诺「按 1→2→3 就能显著消除用户报告的不断跳动」。

## 4. 经修正的因果模型

### 4.1 sticky 链

```text
text_delta / DOM 增高
→ contentKey + ResizeObserver
→ 反复重设 140ms timer
→ 视口暂停,内容累积
→ 模型停顿
→ scrollTop = scrollHeight
→ 阶梯式追底
```

### 4.2 manual 链

```text
用户上滑
→ pinned=false
→ 锚点只记整条消息顶
→ 气泡内部高度/几何变化
→ 消息顶可以不动,内部阅读点被推走
→ 定稿 ID/外壳更换时旧锚点还可直接消失
```

### 4.3 过程卡链

```text
tool_call → running=true → 展开/移到末尾
tool_result(当前全完成) → running=false → 收起
下一批 tool_call → running=true → 再展开
final model_step/reply → stripProcessItems → 卸载
```

### 4.4 横跨三条链的放大器

- 累积文本每次重新进入 Markdown 管线;
- 流式期仍执行代码高亮;
- `.messages { overflow-anchor:none }` 关闭浏览器原生补偿;
- 已完成消息未隔离,整列可随当前 token 重渲染;
- 内联 `onRepairMermaid` 可能额外变更 Markdown components 身份,贡献待 Profiler。

## 5. 动代码前的最小证伪闭环

一次统一 trace 应放在同一时间轴上:

```text
timestamp
sticky/manual
scrollTop / scrollHeight / contentHeight
first visible msg id
visible semantic child rect
process id / running / open / DOM index
assistant UI id / event id / mount generation / root type
Mermaid phase(pre/pending/svg-before-tighten/tightened)
contentKey / RO / model_step / tool_call / tool_result 触发源
```

| 实验 | 隔离目标 | 判定 |
|---|---|---|
| T1 纯文字 sticky | 140ms 独立链 | 停顿后若出现阶梯 `scrollTop`,sticky 链坐实 |
| T2 多轮工具,无 Mermaid | 过程卡链 | 对齐 running/open/DOM index 与可见 rect |
| T3 单 Mermaid manual | 消息内锚点 + Mermaid 阶段 | 消息顶 delta 近 0 而子节点 rect 变,则锚点盲区坐实 |
| T4 定稿身份 | ID/外壳断裂 | 记录旧 key 卸载、新 key 挂载与同帧高度 |
| T5 Mermaid paint | tighten 是否独立可见 | 用 paint/filmstrip,不是仅数 React state |
| T6 Markdown 对照 | 性能 vs 几何 | 比较纯文字、表格、列表、围栏的 long task 与早期节点 rect |

## 6. 给对拍方的简明结论

1. 同意:截图时 manual;sticky 140ms 是另一条确定链。
2. 保留:单张截图不足以判定跳动发生帧始终 manual。
3. 同意:ID/外壳断裂是确定结构缺陷;它证明 remount,不单独证明可见跳幅。
4. 反对:用静态「未闭 fence + 后续正文」样本,证明 append-only 流在闭 fence 时吐出几千字已显示正文。
5. 反对:在无 paint trace 时把 Mermaid 状态序列称为三次可见落位。
6. 新增:真实会话存在多批工具,过程卡可反复收起/复活/移位,必须并列量化。
7. 修正:稳定的对象是当前被封口的 provisional assistant,不是整个 turn 所有消息。
8. 结论:身份连续和 Mermaid 一次提交是高价值候选;其余优先级应由一次统一 trace 决定,不再由报告叙事决定。
