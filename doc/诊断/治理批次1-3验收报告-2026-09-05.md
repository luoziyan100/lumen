## P1: 必须先修的运行与数据问题

### R01: 非法 WebSocket 帧仍能终止服务

对应 A04。位置: [server.ts:56](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/server.ts:56)。

复现: 临时服务使用假 token，合法连接发送仅含字节 `0xff` 的文本帧。Node 子进程退出码 1，错误为 `Unhandled 'error' event / WS_ERR_INVALID_UTF8`。

机制: `decodeClientMessage` 只在 `message` 回调执行；帧解析错误先触发 WebSocket 的 `error`，没有监听器收口。handler 的 try/catch 覆盖不到这个层次。

修复与验收: 传输层关闭坏连接、处理服务器及连接错误；相同坏帧之后另一条合法连接仍可完成请求，服务进程继续存活。

### R02: 收尾写入失败仍阻断清理并导致进程退出

对应 A10。位置: [agent-runtime.ts:774](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/runtime/agent-runtime.ts:774)。

复现: 对 `turn_end` 的 INSERT 注入失败。主动等待的探针得到拒绝，且 `isRunning=true / status=running / active_turn_id 非空`；另一个不调用 `waitFor` 的生产式探针直接 Node 退出码 1，堆栈落在 `execute:775`。

机制: catch 和 finally 都重试可能失败的数据库收尾，`running.delete` 排在它们之后；后台 Promise 没有最终拒绝处理。普通准备失败测试不能证明收尾失败也会释放登记。

修复与验收: 内存释放必须在不依赖持久化成功的清理范围；后台执行拒绝必须被负责该生命周期的宿主消费并报告。分别注入准备、运行、终态提交、日志写入和清理失败。

### R03: 锁文件初始化窗口允许双持有者

对应 A03。位置: [instance-lock.ts:48](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/storage/instance-lock.ts:48)、[instance-lock.ts:67](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/storage/instance-lock.ts:67)。

复现: 在第一个进程 O_EXCL 创建锁文件后、写 PID 前暂停；第二进程调用真实 acquire；再恢复第一个。两个 acquire 都成功，两个进程都仍存活。

机制: 第二进程将空文件当成死锁并 unlink；第一个进程随后写入已经被删除的 inode，误认为自己拥有锁。探针控制调度以放大真实抢占窗口，不是仅调用同进程第二实例。

修复与验收: 使用可靠所有权锁，或完整处理锁发布、持有者识别与过期回收；不能把“暂时读不到 PID”直接解释成可抢占。跨进程测试必须覆盖初始化和回收竞争。

### R04: 关闭监听后过早释放实例锁

对应 A03。位置: [service.ts:199](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/service.ts:199)、[service.ts:219](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/service.ts:219)。

复现: 旧服务执行一个等待中的受控模型任务，调用 `await handle.close()`，再构造同目录新服务。旧 runtime 仍 `isRunning=true`，新服务却已把持久状态扫成 `interrupted`。

机制: dispose 只释放锁；没有停止并等待执行、终止写入能力或关闭数据库。关闭 socket 不等于释放整个执行生命周期。

修复与验收: 停止接收命令，终止或排空主/子执行，完成必要收尾并关闭数据库后才释放所有权。旧执行还可能写入时，新实例不得接管。

### R05: 结束与子代理状态转换仍不是原子的

对应 A08。位置: [task-store.ts:254](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/storage/task-store.ts:254)、[coordinator.ts:337](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/subagent/coordinator.ts:337)。

复现一: 注入清空 active turn 的 UPDATE 失败，得到 `turn_end=1`，但 `active_turn_id` 仍保留。

复现二: 拒绝子代理 completion 事件 INSERT，子代理表已是 done；移除故障后重试 complete，终态幂等判断直接返回。最终 completion 事件和 reminder 都为零，完成通知无法通过普通重试补回。

机制: 只给 `updateTaskStatus` 和 `beginTurn` 加事务，未覆盖结束和子代理完整转换。createTask、子代理 register/markRunning 也仍有分步写入，后者为源码核验。

修复与验收: 每个业务转换的状态、关联事件及必要提醒事实同事务提交，成功后发布；故障回滚后允许正确重试。不能仅测试两种主任务方法就声明全部状态原子化。

### R06: 旧库升级仍可能形成不可重启的中间态

真实隔离 WS 调用 `update_settings`，非法 `provider:"invalid-provider"` 返回成功并写入假设置文件；`submit` 带 `uploads:[null]` 返回错误，但已经留下 queued 任务。数字 projectId、对象 requestId、错误图片与 answers 结构也通过解码器。

### R09: 异步错误丢 requestId，Node 客户端仍会无限等待

对应 A05。位置: [server.ts:151](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/protocol/server.ts:151)、[Node agent-client.ts:218](/Users/zihao/Workspace/Projects/lumen/packages/agent-service/src/client/agent-client.ts:218)。

用真实 server 驱动一个受控拒绝的 listAssets，错误线上消息只有 type/message，没有请求 ID。成功回调恢复了捕获的 requestId，catch 没有；两端 pending Map 无法关联这次错误。UI 只能等自身超时，Node request 没有超时。

Node 客户端未连接时调用 list，send 静默不发送且 Promise 保持 pending。需使用不可变请求级回复函数，统一成功、错误、超时、断线与发送失败的结算。

### R10: 旧连接的迟到 close 会拒绝新连接请求

对应 A05。位置: [UI agent-client.ts:220](/Users/zihao/Workspace/Projects/lumen/packages/ui-client/src/agent-client.ts:220)。

受控 socket 驱动两端真实客户端: close 后立即 connect，在新连接发 list，再触发旧 socket 的 close。新请求被拒绝为连接断开。

pending 表属于 client，但 close 回调没有校验 socket 身份或连接世代。需将请求归属于连接，并忽略旧连接对新连接状态的修改。
